## Problem Statement

Freelancers, agencies, and other crypto-native service businesses need to request a fixed payment, receive it directly, and know which invoice it satisfies. Sharing an account address alone leaves merchants manually reconciling transfers and leaves payers without independently verified receipts. A wallet approval or submitted transaction hash does not prove that the correct payment finalized.

Failures and retries make this harder: a payer may lose the wallet response, verification may be temporarily unavailable, or two people may both pay the same invoice. Merchants need truthful payment status and a way to resolve duplicate payments without giving an invoicing application custody of funds or access to private keys.

## Solution

Build Settiva, an invite-only merchant invoicing MVP with public payment links. Merchants issue immutable invoices; any payer can authorize a direct NEAR token transfer from a separate wallet. Settiva independently verifies the transfer before applying it to the invoice and publishing a receipt.

The required release demonstrates invoice creation, a real finalized testnet transfer, verification, and a receipt. Prefer Circle-listed testnet USDC; after one hour without a usable funded path, use an explicitly allowlisted testnet token labeled “Test token — no monetary value.” Mainnet native USDC support is disabled by default, with live proof an optional, separately authorized milestone.

Keep invoices unpaid until a matching payment is verified. Track uncertainty and errors on payment attempts, preserve evidence across page closure, and accept valid late payments. Retain additional matching transfers as overpayments. The merchant returns each overpayment manually; Settiva verifies that return transfer before reporting it refunded. Preserve the original invoice receipt throughout.

## User Stories

1. As an invited merchant, I want to sign in, so that I can issue and manage my invoices securely.
2. As a merchant, I want access restricted to my own invoices and financial history, so that other merchants cannot inspect or change my records.
3. As an operator, I want public merchant registration disabled, so that the initial demonstration is limited to explicitly invited merchants.
4. As a merchant, I want to enter or connect a receiving account for the selected network, so that payments reach the intended destination directly.
5. As a merchant, I want to explicitly confirm that I control the receiving account, so that I acknowledge the destination before issuing invoices.
6. As a merchant, I want account and token-storage checks before issuance, so that I receive guidance when the destination cannot accept the configured token.
7. As a merchant, I want to approve any required storage registration in my own wallet, so that Settiva never spends on my behalf.
8. As a merchant, I want to create an invoice with one amount, a private client label and description, and an optional due date, so that I can organize my payment requests.
9. As a merchant, I want exact decimal amounts preserved without rounding, so that the requested and verified amounts agree.
10. As a merchant, I want issued payment details to remain immutable, so that a shared link cannot silently change its asset, network, destination, amount, or payment reference.
11. As a merchant, I want a copyable public invoice link, so that I can share a payment request without creating an account for the payer.
12. As a merchant, I want a basic list of my invoices and statuses, so that I can see which requests have been paid.
13. As a payer, I want to open an invoice without registering, so that I can pay with minimal onboarding.
14. As a payer, I want to see the merchant display name, amount, asset, network, receiving account, reference, optional due date, and status, so that I can inspect what I am paying.
15. As a merchant, I want client labels and free-text descriptions kept out of public responses, so that sharing a link does not disclose private invoice information.
16. As a payer, I want testnet and mainnet clearly distinguished, so that I understand whether a transfer involves real funds.
17. As a payer, I want a fallback test token identified accurately, so that I never mistake it for native USDC or an asset with monetary value.
18. As a payer, I want token and NEAR gas/storage requirements explained separately, so that I understand the balances needed to complete payment.
19. As a payer, I want to connect a wallet on the invoice's network and explicitly authorize the transfer, so that I control when funds move.
20. As a payer, I want the transfer to go directly to the merchant, so that Settiva never takes custody of my funds.
21. As a payer, I want to pay on someone else's behalf, so that a finance colleague or another authorized person can settle the invoice.
22. As a payer, I want an opaque payment reference rather than personal information in the transfer memo, so that reconciliation does not publish private invoice content onchain.
23. As a payer, I want a pending attempt shown honestly, so that wallet approval or incomplete execution is not mistaken for payment completion.
24. As a merchant, I want payment independently verified against the invoice, so that an incorrect or fabricated client result cannot mark it paid.
25. As a payer, I want to submit a transaction hash and sender account after a lost wallet response, so that I can recover without paying again.
26. As a payer, I want submitted evidence retained and verification resumed when I reopen the invoice, so that closing the page does not lose my progress.
27. As a payer, I want guidance to retrieve a missing hash from wallet history, so that I know how to recover when Settiva never received it.
28. As a payer, I want temporary verification failures to leave the transfer outcome uncertain, so that the application does not automatically send another payment.
29. As a merchant, I want invalid attempts kept separate from invoice status, so that someone else's incorrect submission cannot block a valid payment.
30. As a payer, I want to pay an overdue invoice, so that an advisory due date does not reject a valid late settlement.
31. As a merchant, I want overdue unpaid invoices identified, so that I can distinguish lateness from expiration or payment failure.
32. As a payer, I want a receipt only after a verified payment is applied, so that the receipt is backed by actual settlement.
33. As an invoice-link holder, I want the receipt to identify the actual sender, recipient, amount, asset, network, transaction, and timestamp with an explorer link, so that I can inspect its evidence.
34. As a payer, I want repeated verification of the same transfer to return the existing result, so that retries do not create duplicate payment records.
35. As a merchant, I want concurrent distinct matching transfers preserved, so that successful payments are not discarded merely because the invoice is already paid.
36. As a merchant, I want only the first successfully recorded matching payment applied to the invoice, so that the original receipt remains stable.
37. As a payer who paid an already-paid invoice, I want my transfer recorded as an overpayment needing refund, so that its successful arrival is acknowledged.
38. As a merchant, I want to see each overpayment and its resolution status, so that I know which duplicate payments still need returning.
39. As a merchant, I want to return the full overpayment from the original receiving account to the original payer using my wallet, so that I retain control over the refund.
40. As a merchant, I want to submit the refund transaction hash, so that Settiva can independently verify the return transfer.
41. As a payer, I want “Refunded” displayed only after the correct return transfer finalizes successfully, so that a submitted hash or failed refund is not mistaken for money returned.
42. As a merchant, I want refund retries to be idempotent and one refund transfer to resolve only one overpayment, so that evidence cannot be reused incorrectly.
43. As a merchant, I want the invoice to remain paid and its receipt unchanged after an overpayment refund, so that resolving an extra transfer does not undo the original settlement.
44. As a merchant, I want the full attempt and refund history to remain private, so that public invoice pages do not enumerate other payers' activity.
45. As a payer, I want to look up one transfer's status and refund proof using its hash, so that I can follow that transfer without exposing the entire invoice history.
46. As a merchant, I want knowledge of a transaction hash to confer no merchant privileges, so that public blockchain data cannot authorize refunds or private-data access.
47. As a payer who sends an incorrect amount or reference, I want a clear mismatch result and guidance to resolve it with the merchant, so that I understand why the invoice was not credited.
48. As an operator, I want the backend to block new mainnet invoices and in-app checkout by default, so that changing client UI cannot enable live payment collection.
49. As a payer with an existing mainnet transfer, I want verification and existing receipts available when checkout is disabled, so that disabling new payments does not erase settlement evidence.
50. As a reviewer, I want reproducible setup instructions and genuine testnet evidence, so that I can evaluate the demonstration without a private mainnet wallet.
51. As an operator, I want secrets excluded from frontend code and committed artifacts, so that deploying the demo does not expose privileged credentials.
52. As an operator, I want rate-limited verification and lookup with useful non-sensitive diagnostics, so that public submissions cannot trivially overwhelm the application or leak invoice data.
53. As a reviewer, I want mainnet claims tied to separately authorized, genuine evidence, so that an implemented adapter is not represented as demonstrated mainnet settlement.

## Implementation Decisions

1. **Starting point and delivery scope.** The repository currently contains product documentation, a domain glossary, agent configuration, and two ADRs; it has no application implementation, dependency manifest, migrations, or test suite. Build the required MVP from this starting point. Dashboard enhancements, exports, and other P1 features are deferred until required behavior succeeds.
2. **Stack and modules.** Use Next.js with TypeScript, Tailwind CSS, Supabase Auth/Postgres/RLS, Vitest, and a deployment target of Vercel. Organize around merchant access/invoice issuance, payment verification and allocation, refund verification, and public/private read projections. Keep a small application interface; avoid an indexer, bridge, custodial module, or bespoke smart contract. Verify current wallet/library APIs before selecting versions; the PRD's candidate is HOT's NEAR connection library with near-api-js or direct RPC as appropriate. No prototype was produced.
3. **Merchant access.** Permit explicitly invited merchants only, enforced server-side. Validate ownership of the invoice/profile for private reads and writes. Accept manual receiving-account entry with explicit control/destination confirmation; format and storage checks do not establish cryptographic ownership. The payer needs no Settiva account, and the private client label does not restrict which wallet can pay.
4. **Asset configuration.** Maintain an explicit server-owned per-network token allowlist. Validate live metadata, expected identity, decimals, storage registration, and available balances before claiming a funded transfer path. Recheck PRD contract candidates against official sources before use; reject bridged USDC.e and unknown assets. Time-box Circle testnet USDC funding investigation to one hour, then use the agreed separately allowlisted, visibly labeled test token if necessary. Mainnet accepts native Circle USDC only. Freeze the actual asset identity and decimals on issuance; never silently substitute an existing invoice's asset.
5. **Invoice issuance and state.** Store merchant ownership, private client label/description, advisory due date, currency, actual asset symbol, network, token contract, receiving account, positive exact atomic amount, decimals, a unique high-entropy payment reference, and timestamps. Parse decimal input exactly; store atomic amounts as integer strings and avoid floating-point arithmetic. Issued network, contract, destination, amount, and reference are immutable. Invoice state is unpaid or paid; overdue is derived from an unpaid invoice's due date and does not disable checkout. Acceptance of valid late payment is independent of verification timing relative to the due date.
6. **Wallet transfer.** Obtain payment details from the stored invoice, display them, and require explicit wallet authorization on the correct network. Construct one intended NEP-141 ft_transfer function call to the configured token contract, with the merchant receiving account, exact amount, and opaque payment reference in its arguments. Require the prescribed one-yoctoNEAR deposit and a gas budget validated against current wallet guidance. Use one consistent memo encoding. No personal data belongs in the memo. The application never handles private keys or signs for a user.
7. **Verification contract.** Public verification takes an invoice identifier, transaction hash, and claimed sender account only. Derive all expected payment facts from the stored invoice and configured network. Independently query final transaction execution and relevant receipts; verify the submitted hash, actual sender, token-contract destination, single allowed action, deposit, recipient, amount, memo, finality, and successful execution. Reject mixed/ambiguous transactions and wrong assets or networks. Check that settlement is not earlier than invoice creation where reliable timestamps exist; if that evidence is unavailable, disclose the limitation and retain the exact unguessable reference plus transaction uniqueness as the binding invariant.
8. **Attempt persistence and recovery.** Persist submitted transaction evidence, invoice association, and verification outcomes separately from invoice status. Distinguish pending confirmation, execution failure, mismatch, temporary RPC unavailability, and verified results. Retry verification while the page is open and resume from retained evidence after reopening, subject to rate limits. Without a known hash, provide wallet-history recovery guidance. No background wallet monitoring and no automatic repeat transfer. A bad submission never downgrades a paid invoice or blocks a later matching payment.
9. **Payment allocation and concurrency.** Retain every distinct fully matching verified transfer. Enforce uniqueness of network plus transaction hash and at most one applied payment per invoice. Use a database transaction and invoice row lock, or equivalent atomic enforcement, to allocate the first successfully recorded matching payment and mark the invoice paid together. Later distinct matching transfers are overpayments. Verification order determines the applied payment, not earliest onchain timestamp. Same-hash retries return the existing result; two distinct concurrent payments are both retained with one applied. The same transaction cannot satisfy another invoice.
10. **Duplicate-payment refunds.** Each overpayment starts with refund-needed resolution. The invoice-owning merchant manually authorizes a separate return transfer, then submits its hash for verification. Derive the original invoice receiving account as refund sender, original payment sender as recipient, full overpayment amount, and identical asset/network from stored evidence. Independently verify successful final execution and exact return details before marking refunded. Persist proof linked to its specific overpayment, bind it to that return obligation, and prevent one return transfer resolving multiple overpayments. Pending or failed verification leaves resolution outstanding. Retain the applied payment, invoice paid state, and original receipt throughout. Settiva neither initiates automatic refunds nor guarantees merchant action.
11. **Refund eligibility.** The verified refund workflow covers additional distinct fully matching payments only. Two correct 10-token transfers for a 10-token invoice create one applied payment and one refundable overpayment. One 20-token transfer, a partial amount, or a wrong reference is a mismatch, requiring resolution directly with the merchant outside this workflow. A refund from a different source account or to a different recipient is not accepted under the MVP rules.
12. **Public/private projections.** Public invoice details include merchant display name, amount, asset, network, receiving account, payment reference, optional due date, and status. The original receipt additionally exposes applied-payment proof, actual sender/recipient, transaction timestamp, and the network-correct explorer link. Client labels and descriptions are merchant-private. The invoice-owning merchant sees the complete attempt/payment/refund history; public invoice and receipt reads never enumerate it. A rate-limited lookup scoped to an invoice and one hash returns only that transfer's status and relevant payment/refund proof. A public hash does not authenticate the payer or authorize private access or refund submission.
13. **Application operations.** Expose authenticated merchant profile configuration and invoice create/list/history operations; public invoice/payment configuration and original receipt reads; public payment-evidence submission; a public specific-transfer lookup; and an authenticated merchant refund-evidence submission. Keep authorization and canonical validation on the server. Mutation inputs cannot supply trusted paid/refunded state or replace expected token, destination, or amount. Refund submission is restricted to the invoice-owning merchant even though evidence may be publicly inspectable.
14. **Mainnet controls.** Mainnet payments are disabled by default. Backend enforcement rejects new mainnet invoices and reports in-app checkout unavailable while preserving existing invoice details, original receipts, and verification of genuine transfers against already-issued invoices. Client permissions come from the server. Mainnet activation and any real-funds demonstration require a separate explicit human decision; this spec does not authorize either. Verification of existing evidence does not initiate a transfer.
15. **Persistence and isolation.** Maintain merchant profiles, immutable invoice payment terms, durable attempt evidence, verified payments with applied/overpayment allocation, and refund evidence/resolution linked to overpayments. Enforce transaction/refund uniqueness and allocation constraints in Postgres rather than relying on client checks. Use RLS and server authorization for merchant isolation, and deliberately narrow public projections. Keep privileged Supabase credentials server-only. Use structured diagnostics that omit private invoice content and secrets.
16. **Deployment and evidence.** Deliver a reproducible testnet setup, environment-variable documentation, license, working README, negative-test instructions, and a deployable demonstration with clear asset/network labels. A real testnet transfer and duplicate-payment/refund flow must support release claims; deterministic fixtures are not live proof. Repository publishing, deployment, wallet signing, mainnet activity, social posting, and event submission retain their existing authorization requirements. External wallet/hash recovery may be documented if wallet integration fails, but it must be disclosed as incomplete in-app checkout.

## Testing Decisions

Testing-seam status: approved by the user. The primary seam is the application's HTTP interface, supplemented by browser/wallet smoke coverage and genuine testnet payment/refund proof.

1. **Primary seam.** Exercise the application through its HTTP interface, the highest useful externally observable seam for invoice operations, evidence submission, receipts, and authorization. Use a real isolated Postgres/Supabase test environment with actual constraints and RLS. Control NEAR RPC responses at the external RPC adapter for deterministic success, failure, finality, metadata, storage, and outage scenarios. Do not mock internal helpers or replace the persistence rules being tested.
2. **What makes a good test.** Assert observable responses, access permissions, durable results visible through the interface, stable receipts, and successful recovery after retries/reopening. Tests should survive internal refactoring. Prefer complete meaningful scenarios over mirroring functions, private call order, or implementation structure.
3. **Prior art.** There are no existing application modules, testing seams, fixtures, or tests to extend. The agreed PRD acceptance scenarios and ADR invariants supply the initial behavioral cases; no prototype code provides prior art.
4. **Invoice and access scenarios.** Test invited/uninvited access, cross-merchant isolation, receiving-account/storage failures, exact amounts, frozen invoice terms, late payment, and overdue display. Exercise both application authorization and exposed Supabase access policies so bypassing the application does not expose private rows or writable settlement state.
5. **Payment verification scenarios.** Exercise successful final settlement; wrong network, token, bridged asset, sender, merchant, amount, memo, deposit, or action; native NEAR transfer; ambiguous batches; failed relevant receipts; optimistic/unfinalized execution; missing transactions; and RPC outage. Invalid attempts cannot prevent a subsequent valid payment or downgrade an already-paid invoice.
6. **Persistence and race scenarios.** Verify same-hash idempotency, rejection of cross-invoice reuse, concurrent requests for the same transaction, concurrent distinct matching transfers, first-recorded allocation, unchanged original receipt, and evidence recovery after page closure. Use real database constraints under concurrency, not in-memory approximations.
7. **Refund scenarios.** Test a second verified matching transfer becoming refund-needed, a correct merchant-authorized full return becoming refunded only after verification, and failure for wrong source, recipient, network, asset, amount, missing/failing/unfinalized evidence, unauthorized merchant, or reused refund proof. Idempotent refund retries must preserve the original invoice and receipt. A single double-amount transfer and a wrong-reference transfer never enter this workflow.
8. **Privacy and flags.** Inspect response bodies for prohibited client labels, descriptions, other attempts, and other payers' refund history. Test one-hash lookup without allowing enumeration or merchant privileges. Test server-side mainnet issuance rejection with a manipulated client and continued verification/read access for already-issued invoices while checkout is disabled. Verify fallback-token identity in invoice and receipt output.
9. **Browser/wallet coverage.** Add a small browser-level smoke test of merchant issuance, public checkout, pending/recovery presentation, original receipt, and one-transfer refund lookup. Control the wallet interaction for repeatability while checking explicit authorization and network display. This complements the primary HTTP seam rather than duplicating every backend scenario through the browser.
10. **Real proof.** Separately run an authorized wallet-driven testnet flow with funded accounts: issue invoice, submit an actual finalized payment, verify receipt, submit a second matching payment, return it manually, and verify refunded resolution with the original receipt intact. Preserve genuine transaction evidence and actual asset/network labels. A mainnet smoke test is optional and separately authorized; never make routine tests spend real funds.

## Out of Scope

- Public merchant registration; teams, advanced multi-tenancy, or cryptographic receiving-account ownership attestations.
- Background wallet monitoring, automatic discovery of transfers whose hashes never reach Settiva, or automatic repeat payments.
- Custody, private-key handling, automatic signing, automatic refunds, chargebacks, or guaranteed merchant refund fulfillment.
- Partial payments, aggregation of mismatched transfers, refunds for a single wrong-amount transfer, wrong-reference reconciliation, and general refund/dispute workflows beyond duplicate full payments.
- Invoice expiry, due-date payment cutoffs, and changes to issued payment terms.
- Broad public mainnet payment collection or a claim of production/commercial readiness. Mainnet proof is optional rather than required for release.
- Cross-chain checkout, NEAR Intents, bridges, swaps, gas abstraction, fiat ramps, bank payouts, subscriptions, monetization, and accounting integrations.
- Dashboard enhancements, CSV exports, printable/PDF receipts, email reminders, and hosted mainnet samples until the required MVP succeeds.
- Automated hackathon submission, social publishing, repository visibility changes, or deployment merely by publishing this spec.

## Further Notes

- This spec synthesizes the accepted design interview and Settiva PRD v2.3. The glossary is authoritative for merchant, payer, invoice, payment attempt, verified payment, applied payment, overpayment, refund, overdue invoice, and receipt. ADR 0001 keeps attempt outcomes separate from invoice status; ADR 0002 retains overpayments and verifies merchant-authorized returns.
- Required release scope includes duplicate-payment refund tracking and verification. It must not be silently deferred under the earlier general post-hackathon refund exclusion.
- A successful real testnet flow satisfies the required demonstration. After the one-hour funding investigation, the fallback must be visibly a test token with no monetary value; it cannot support a native-USDC or mainnet-settlement claim.
- Token availability, live metadata, exact wallet/RPC APIs, selected dependency versions, and operational setup remain implementation-time verification tasks. This document does not claim that accounts are funded, deployment exists, or any transfer/refund has already occurred.
- Preserve the PRD's controlled-demonstration and jurisdiction-review limits. The software is not represented as a licensed payment service, and technical settlement evidence does not establish authorization for commercial use. Recheck event requirements when preparing an actual submission.
- Target issue tracker: GitHub Issues in yynfz/settiva. Publish this spec with the ready-for-agent label; it does not need another triage pass. Publishing the spec does not create implementation tickets or begin implementation.
